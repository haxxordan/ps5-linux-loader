# Firmware 12.70 loader handoff

Status: one-console 12.70 NPT clear, kernel-text dump, and bounded HV code
capture. No 12.70 Linux boot or second HV control transfer has been demonstrated.

## Scope and pinned inputs

- Target: launch-model PS5 Phat (`sceKernelGetMainSocId() == 0x840f60`), firmware
  12.70. Do not generalize this evidence to Slim or Pro.
- Loader base: `ps5-linux/ps5-linux-loader` commit
  `64637c177eaed277fb6ccce394cbb29dd047b893`.
- Tested NPT clear: `haxxordan/Byepervisor-Reborn` branch `main`, commit
  `00dfdf3012d677fe5bd4030e6e2870f168eaa8ec`. Its
  `byepervisor-1270.elf` (SHA-256
  `633cb2d8788fbefdafe3798b2e6c9bfc4bb52057453e1caa16b36f78c00d445e`)
  completed an S3 cycle, processed 16 VMCBs, cleared nested paging, verified
  kernel-text readability, and returned to PS5 OS on one launch-model console.
  The separate `fw-12.70` Byepervisor branch at
  `2130324675137ff4af5b16e54b1523cf10b2296f` has not been hardware-tested.
- Offline kernel text: `PS5-12.70-ktext-95-1791948146.bin`, 0xd50000 bytes,
  SHA-256 `9d79abbbb4dec7e077d5c65031b84b38955306d0772a7007c675d6e27a446c61`.
  Its companion log records firmware `0x12700001`, text base
  `0xffffffffc1070000`, and `end,complete=1`. Neither file is stored here.

## Control-transfer boundary

The existing loader reaches Linux by preparing `shellcode_kernel`, patching a
physical hypervisor VMEXIT handler, then calling `smp_rendezvous` with a
VMMCALL callback on every CPU. `shellcode_hv` takes over on those exits and
eventually jumps to Linux `startup_64`. That path is proven only through 7.61.
The 12.70 Byepervisor result stops earlier: it returns from the resume AP
stub after changing VMCBs. Kernel-text access does not prove that a later
VMMCALL can safely enter our own hypervisor code.

| Requirement | Evidence now | Gate before use |
| --- | --- | --- |
| Resume entry and NPT clear | One-console 12.70 run; 16 VMCBs and marker recorded | Recheck firmware/model and exact source commit |
| Kernel text image | Full dump, size/hash and log checked | Match candidate bytes to the live console |
| `smp_rendezvous` callback path | Offline wrapper at text+`0xb8fbc0` shifts four arguments, loads the CPU set at text+`0x3d30228`, and tail-jumps to text+`0xb8f980`; the callee has setup/action/teardown indirect calls | Match these bytes on the live console and check the callback/CFI contract before calling it |
| VMMCALL wrapper/callback | Candidate `hv_mp_startup_call` at text+`0xc9dfb0` disassembles to a function that sets `eax=15`, executes VMMCALL at +`0xc9dfc2`, and returns | Verify its live bytes and semantics; this is not the all-core callback or HV takeover proof |
| HV VMEXIT handler and code cave | PA `0x62820000..0x6284ffff` captured live; the old 13.60 handler address is a different 12.70 function, and the old byte lead has three PCI-context matches | Identify handler by control flow and callers before considering any patch; verify a separate cave if that route is chosen |
| Safe second root-mode transfer | Not demonstrated | Marker-only diagnostic on one selected exit, with recoverable result |
| Linux staging and hardware setup | Old-firmware code is available | Audit memory ranges and device setup after the marker test |

## First experiment

1. Analyze the 12.70 kernel dump for `smp_rendezvous` and its VMMCALL
   callback. The wrapper and callee have now been identified offline; the
   callback to use and live bytes remain open.
2. Study the tested Byepervisor resume AP entry as a direct root-mode route.
   The older VMEXIT-patch route needs independent handler identification;
   the 13.60 address and six-byte signature did not identify it on 12.70.
3. Build a read-only preflight that checks model, firmware, dump-derived
   kernel signatures, HV signatures, and staging ranges. Any mismatch must
   abort before a write.
4. Only then build a diagnostic that records a durable marker at a deliberate
   second root-mode entry. Do not stage a Linux image or patch a shared
   dispatcher as part of that first diagnostic.

The old loader's `patch_hv()` writes an unconditional jump into the shared
VMEXIT handler. It is a reference for the eventual boot contract, not a safe
12.70 implementation. The 13.60 loader experiment also contains a different
resume AP route (`hv_boot`); its own README reports NPT clear on hardware but
does not establish a completed Linux boot. That route warrants analysis before
copying an old VMEXIT address or patching a shared dispatcher.

### First offline result

The Byepervisor 12.70 candidate table names `hv_mp_startup_call` at
text+`0xc9dfb0`. The pinned dump contains `55 48 89 e5 53 48 89 d3 48 89 f1
b8 0f 00 00 00 89 fa 0f 01 d9 5b 5d c3` there. Disassembly shows a
normal function prologue, argument moves, `eax=15`, VMMCALL, and return.
This corroborates that particular wrapper offset in the offline dump. It
does not show how the hypervisor handles the exit or establish a safe place
to redirect it.

### Rendezvous identified offline

The 12.70 dump has a function at text+`0xb8fbc0` whose full 29-byte body is
`55 48 89 e5 49 89 c8 48 89 d1 48 89 f2 48 89 fe 48 8b 3d 51 06 1a 03
5d e9 a3 fd ff ff`. It moves the four callback arguments one register to the
right, loads the CPU-set word from text+`0x3d30228` into `rdi`, and tail-jumps
to text+`0xb8f980`. That five-argument function stores the three callbacks
and invokes them through indirect calls at text+`0xb8faf7`, `0xb8fb1c`, and
`0xb8fb41`. Two independent call sites at text+`0xc94e80` and `0xc94eaf`
call the wrapper with four arguments. Together these give a strong offline
identification of `smp_rendezvous`; the CPU-set address and callback semantics
must still be checked live before use. Its callback path contains CFI checks,
so an injected callback cannot be assumed callable.

`tools/fw1270_kernel_preflight.py` repeats the pinned dump hash, signature,
relative target, and callback-call-site checks without touching the console:

```sh
python3 tools/fw1270_kernel_preflight.py /path/to/PS5-12.70-ktext-95-1791948146.bin \
    --log /path/to/PS5-12.70-ktext-95-1791948146.txt
```

### First hypervisor acquisition diagnostic

`diagnostics/fw1270_hv_page.c` is a one-page acquisition diagnostic. Its
default target is PA `0x62882000..0x62882fff`, which contains the `pcpus[0]` qword at
PA `0x62882a60` read successfully by the 12.70 AP probe. It records a synced
USB log before and after the 8-byte probe and the 4 KiB page read. It checks
12.70 and the launch-model SoC, validates that the page contains the same
qword, and writes one binary page only on success. It has no HV patch or
Linux-boot path. Its read target is unchanged, but the SDK's
`kernel_copyout()` can modify exploit-pipe bookkeeping and an unmapped read
can crash the console.

The source builds with the official `ps5-payload-dev/sdk` v0.44 release using
LLVM 23. The ELF used for the first live test had SHA-256
`e398d7bfac14bf5c5192e65c0730ef0618b46037c6d0fb43f0d2be0ce6d63fab`.
The source subsequently gained compile-time page selection; its rebuilt
default ELF has SHA-256
`5b7423febdc70561b523ed9100e932bf4e4149be7ffe109177794372fefc59ac`.
ELFs are ignored by Git. This diagnostic is intended only
after the tested 12.70 text-map apply and NPT clear sequence has completed
in the same boot, with `survey_count=16` and `cleanup=0` in its result. The
diagnostic checks the SDK's text/data gap without reading kernel text. A
complete result is a 4096-byte `.bin` and
a matching `.txt` ending `end,complete=1,bytes=0x1000`; preserve and hash both
on the workstation. One page corroborates access, not the VMEXIT handler or
code cave. Any further page needs its own evidence and bounded diagnostic;
the 13.60 addresses are leads, not 12.70 offsets.

Build with the PS5 payload SDK: `make -C diagnostics
PS5_PAYLOAD_SDK=/path/to/ps5-payload-sdk LLVM_CONFIG=/usr/bin/llvm-config`.

### First live hypervisor page

On the launch-model 12.70 console, the pinned one-ELF NPT clear completed
again with `survey_count=16`, zero rejects, `cleanup=0`, and readable kernel
text. Its USB record is `PS5-12.70-byepervisor-1270-94-1792000285-488691609.txt`
(SHA-256 `889a7a1bc8f5ab3eb9df1bc6a53bd464140bc6f820aef179affa5302de9da44a`).
The first HV diagnostic then completed in the same boot. Its log
`PS5-12.70-hv-page-103-1792000462-162075463.txt` (SHA-256
`b50c5c3d4f0b83eff6fadc7b11a268490f5483bbab53ebaabbf85a29ca72100c`)
records firmware `0x12700001`, SoC `0x840f60`, direct-map base
`0xffffad4700000000`, PA `0x62882000`, an 8-byte read result of zero (success)
with value `0x0000687864000000` at PA `0x62882a60`, and a complete 4 KiB page
read. The paired binary `PS5-12.70-hv-page-103-1792000462-162075463.bin`
is exactly 4096 bytes, SHA-256
`37550689846eda599a76327c17d297c1bb5f03a5377272ce5aa5705c838cf7e4`.
Its qword at offset `0xa60` matches the log; the next 15 qwords form a
`0x2000`-spaced pointer sequence. Both files were copied from USB by FTP and
preserved outside the Git repository. This proves the bounded post-resume
HV direct-map read path on this console. It does not identify a 12.70 VMEXIT
handler or a code cave.

### Live 12.70 HV code window

`fw1270_hv_3d000.elf` (SHA-256
`686a79918d9711a6a62ec5b7d9a4751670075ee8ae9edc1e7f31cc01f7bcf61f`)
read PA `0x6283d000..0x6283dfff` after the same NPT clear. Its log
`PS5-12.70-hv-page-105-1792000776-728512652.txt` has SHA-256
`95b74c4d8cf311b41fd82dc059931a18aabfd8b6dd920c1cdd876c9b9a50e6e8`;
the 4096-byte binary has SHA-256
`2747a128043c4e8465d7ecd79c52c97efa57ff2a3524c116f1985dd83d2920e4`.
The 8-byte probe at `0x6283d800` returned `0x56415741e5894855`, a normal
function prologue (`55 48 89 e5 41 57`), not the 13.60 lead bytes.

`diagnostics/fw1270_hv_code_window.c` then captured 48 consecutive pages,
PA `0x62820000..0x6284ffff`, with an `fsync` checkpoint before and after each
read. The live ELF had SHA-256
`c781ec575de3e56d3fd3dab41fad65dfc4b03df870da45c16f21aad30b988b99`.
The log `PS5-12.70-hv-code-106-1792000900-240737039.txt` ends
`end,complete=1,pages=48,bytes=0x30000` and has SHA-256
`da87dd1490d2e39200c96408ec7fc48771892531c06d0768f1e671d485fd2d09`.
The binary is exactly 196608 bytes, SHA-256
`6b07a3cd4d41c29564c86d5335087de5383c6d24b52a14b53f5369da5c2ad910`.
Both files were copied from USB and retained outside the repository.

The 13.60 offset `0x6283d800` is not transferable. The six-byte pattern
`ba fc 0c 00 00 ed` occurs at 12.70 PAs `0x6283cce1`, `0x6283d5b9`, and
`0x6283d620`. Disassembly shows PCI configuration I/O around these matches,
including writes to port `0xcf8`; they are not sufficient evidence of a
VMEXIT dispatcher. A byte match without the function's control-flow role is
not an offset verification. No HV code cave has been verified here.

### Storage for later boot tests

Upstream supports a USB drive as the Linux boot medium and recommends an
external SSD. M.2 is optional. The current offline and marker work does not
need any Linux boot drive. Keep the diagnostic USB's only-copy artifacts until
they are inventoried; the pinned full dump and companion log already have
verified workstation copies outside this repository.
