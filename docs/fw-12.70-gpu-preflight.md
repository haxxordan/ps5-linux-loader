# Firmware 12.70 GPU and display preflight

Status: investigation plan. There is no 12.70 Linux boot or AMDGPU log yet.
Target is the launch-model PS5 Phat in `fw-12.70-handoff.md`.

## What the reported symptom establishes

Soniciso's report, copied by the user into a prior chat, says Linux runs but
there is no GPU output. It does not include an AMDGPU probe log, PCI inventory,
DRM connector state, display mode, EDID, or evidence of GPU rendering. A black
HDMI screen alone cannot distinguish a Linux boot failure, failed AMDGPU probe,
failed display link, or a monitor/mode mismatch.

The current pLabs5/pLinux5-NG `off_1320.c` contains candidate 13.20 offsets
for `G_VBIOS`, `FUN_TRANSMITTER_CONTROL`, `FUN_MP3_INITIALIZE`, and
`FUN_MP3_INVOKE`. Its kernel boot code calls all four during the display
handoff. Those offsets were added to the published source by 2026-10-14;
their presence does not prove that the calls succeed on hardware or that the
Linux AMDGPU driver initializes. The current NG README says only 13.20 is
supported and still describes full Linux support as unfinished. NG's
`source/hw/gpu.c` implements GPU DMA for its payload; that is separate from
Linux's AMDGPU/DRM display path.

## Existing display contract

The 3.00–7.61 loader's `shellcode_kernel/boot_linux.c` performs these steps
before transferring control to Linux:

1. Copy 64 KiB from `G_VBIOS` to physical `0xC0000`.
2. Call `FUN_TRANSMITTER_CONTROL` with command `0x4c` to enable the DP PHY.
3. Call `FUN_MP3_INITIALIZE(0)`, then `FUN_MP3_INVOKE` with command IDs 21
   (HDCP packet) and 22 (output enable).

The PS5 Linux kernel patch then reads its VBIOS at `0xC0000`, recognizes PCI
device `1002:13da`, adds PS5 AMDGPU discovery data, calls the transmitter
control code through its SVM guest wrapper, and supplies custom HDMI/DP mode
handling. Missing or invalid VBIOS and failed transmitter/MP3 setup can
therefore produce a dark screen before any ordinary EDID or mode workaround
is relevant. The upstream loader also documents white-LED/black-screen cases
that depend on `video=DP-1:...`, HDCP, monitor choice, and
`amdgpu.force_1080p=1`.

## 12.70 work we can do before a Linux boot

- Locate `G_VBIOS` independently in 12.70 kernel data. Validate a `55 aa`
  option-ROM header, sane image length, AMD/ATOMBIOS markers, and a complete
  64 KiB read. Record the source address and SHA-256. Do not copy another
  firmware's address into the loader.
- Identify `FUN_TRANSMITTER_CONTROL`, `FUN_MP3_INITIALIZE`, and
  `FUN_MP3_INVOKE` from 12.70 code and call sites. Check the parameter layout
  and command IDs against the old loader. The pinned 12.70 kernel-text dump
  covers `0xd50000` bytes, enough to analyze candidate functions, but not
  the VBIOS data region.
- Add boot-stage records for the VBIOS copy and each display call, including
  return values. A failed call should be visible in a persistent log.
- Prepare a headless Linux boot observation path (UART or network, after
  confirming the relevant 12.70 hardware and kernel setup). HDMI alone is
  inadequate for deciding whether Linux, AMDGPU, or the bridge failed.

The 13.20 NG table and the 13.60 experimental fork provide search leads only.
The 13.60 fork's display functions remain unset in its own 13.60 table; its
black screen does not establish a Linux AMDGPU defect.

## First Linux boot: evidence to collect

Keep the initial display mode conservative: one known 1080p/60 display, a
known cable, and a recorded HDCP setting. Record the exact kernel image,
PS5 patch revision, firmware files, boot command line, and VBIOS hash.
Collect the following through the headless path, even if HDMI is black:

| Evidence | Question answered |
| --- | --- |
| Last boot-stage marker and early kernel log | Did control reach Linux, and how far? |
| `lspci -nn -vv -d 1002:` | Is the GPU enumerated with usable BARs? |
| Full `dmesg` with `drm.debug=0x1e log_buf_len=4M` | Did AMDGPU probe, load firmware, find VBIOS, and initialize display? |
| `/sys/class/drm/`, connector `status` and `modes` | Did DRM create a device and see a display mode? |
| EDID binary, if exposed | Is the monitor/bridge supplying coherent modes? |
| `/dev/dri/card*`, `/dev/dri/renderD*` | Is a DRM display or render node available? |

Interpret the evidence in stages:

| Result | Next investigation |
| --- | --- |
| No Linux marker/log | Boot handoff, memory map, root filesystem, or logging path. |
| Linux runs; GPU absent from PCI | PCI/IOMMU/VRAM initialization and handoff. |
| PCI device present; AMDGPU probe fails | VBIOS, firmware, MMIO/BARs, PSP/SMU, or kernel patch mismatch. |
| AMDGPU and render node work; connector absent/dark | DP PHY, MP3/HDMI bridge, HPD/EDID, mode programming. |
| Connector active; picture black or corrupted | Scanout format, buffer, link timing, bridge mode, monitor compatibility. |

Only after the relevant stage passes should we try the upstream mode remedies
(`video=DP-1:...` removal, HDCP toggle, monitor change, or force 1080p).
